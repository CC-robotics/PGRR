# 作业二：恢复进展检查接口原型

## 已完成的实现

新增纯 Python 模块：

`packages/ramp_core/ramp_core/recovery/progress.py`

它目前没有接入 ROS、状态机或线上 PGRR，因此不会改变已有模型和运行结果。模块只把
一个恢复循环结束时应回答的问题整理成可测试接口。

## 为什么不是再写一个“前进距离计数器”

现有 `ObservableGoalProgressBudget` 已经能检查机器人是否相对原始目标累计前进，并防止
机器人“后退再回到原处”反复刷新恢复预算。状态机也已经具有 rejoin 次数和恢复序列
总时限。新诊断发现的问题，是很多循环能 rejoin，却没有真正解决任务，因此新接口补充
的是循环结果评价，而不是复制已有预算。

## 接口输入

`RecoveryCycleEvidence` 只使用运行时可观察量：

- 循环开始时到原始目标的距离；
- 循环结束时到原始目标的距离；
- 危险分数连续清除的帧数；
- 当前规划器目标是否已经恢复为原始目标；
- rejoin 后多久再次触发恢复，没有观察到则为 `None`。

它不读取仿真器中的真实行人位置等 privileged 字段，因此未来可以用于测试和真实机器人。

## 输出判定

`assess_recovery_cycle` 同时输出独立布尔检查，并按顺序给出一个主要判定：

1. `ORIGINAL_GOAL_NOT_ACTIVE`：临时目标尚未正确恢复；
2. `HAZARD_NOT_CLEARED`：危险没有连续清除；
3. `INSUFFICIENT_TASK_PROGRESS`：没有充分推进原始任务；
4. `RAPID_RETRIGGER`：看似恢复，但很快又触发；
5. `EFFECTIVE`：以上检查全部通过。

这种顺序方便定位最早失效的接口，但所有布尔量仍被保留，不会因单一标签丢失信息。

## 阈值处理

原型故意不提供默认阈值。调用方必须明确传入：

- 最小原始目标进展；
- 最小连续安全帧数；
- 快速再次触发的时间窗口。

测试中的 `0.2 m / 4 帧 / 3 s` 只是合成用例输入，不是新算法配置，更没有写入 Arena
或冻结发布版本。正式候选值只能从新的 train/validation 协议中确定，不能使用冻结 test
调参。

## 已覆盖测试

- 有效循环；
- 原始目标未恢复；
- 危险未清除；
- 进展不足；
- 快速再次触发；
- 后退不能算进展；
- 非法阈值和非法观测值。

连同原有恢复选项和状态机测试，本轮共 `176 passed`。这证明接口行为确定且没有破坏
现有核心回归，但不证明算法性能改善。
