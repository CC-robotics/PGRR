# PGRR 阶段工作汇报与后续实验待确认事项

整理日期：2026-09-16  
用途：向教授汇报上次交流后已经完成的工作、目前遇到的问题，以及后续实验需要确定的事项。

## 一、目前已经完成的工作

### 1. 已跑通完整的 PGRR 实验流程

我们已经完成从场景配置、Arena 仿真运行、Base/PGRR 配对测试、结果记录、
恢复行为诊断到论文数据整理的完整流程。现有 Docker、ROS2、Arena 和 PGRR
运行环境可以正常工作，Base 和 PGRR 均能在相同场景与相同种子下运行。

所有实验结果都会保留明确的终止状态，包括成功到达、碰撞、超时、规划失败
以及仿真器或重置失败。我们没有删除失败实验，也没有用新的运行替换不理想
的结果。

### 2. 已完成正式冻结实验及其统计分析

现有正式评测包含 600 个 episode，Base、Standard、Heuristic、Uniform BC 和
PGRR 五种方法分别测试相同的 120 个条件。主要结果为：

| 指标 | Base | PGRR |
|---|---:|---:|
| 成功到达 | 85/120 | 109/120 |
| 碰撞 | 35/120 | 0/120 |

PGRR 相比 Base 显著提高了成功完成率并消除了这组实验中的碰撞。但在双方都
成功的条件中，PGRR 平均慢 15.88 秒、路径长 1.89 米，并且角加加速度更高。
因此论文既要报告安全与完成收益，也必须报告效率和平滑性代价。

这组正式结果已经冻结。我们没有修改其测试集、最终 checkpoint 或算法阈值。

### 3. 已完成八类新场景原型的生成和真实运行

为了寻找教授要求的八个优势场景，我们新设计并运行了八类 train-only
扩展原型。每个场景都实际生成了 Arena 文件，并完成 Base/PGRR 最小配对：

| 结果 | Base | PGRR |
|---|---:|---:|
| 成功到达 | 0 | 0 |
| 碰撞 | 6 | 0 |
| 超时 | 2 | 7 |
| 规划失败 | 0 | 1 |

这些场景能够使 Base 暴露碰撞问题，PGRR 也确实避免了碰撞；但 PGRR 没有
完成到达。因此，这八类场景目前只能作为困难场景和失败诊断材料，不能算作
“PGRR 可以处理而 Base 不能处理”的八个合格场景。

### 4. 已分析 PGRR 在新场景中失败的原因

对恢复过程进行逐步检查后发现：

- PGRR 在 7/8 个新场景中确实触发了恢复，不是检测器没有工作；
- 共记录 235 个恢复决策，但方向性临时子目标只出现 4 次；
- 大部分恢复动作是 WAIT、BACKUP 或重复进入恢复；
- 在两个重点失败位置中，许多方向候选首先被安全扫描排除，剩余候选又被
  方向让行约束删除，最后没有可执行的临时子目标；
- PGRR 经常把 Base 的“碰撞”转化为“长时间等待或规划失败”，却没有真正
  恢复并重新到达原始目标。

目前最有证据支持的判断是：主要障碍不是 PGRR 没有发现风险，而是恢复阶段
可用的方向动作太少，并且恢复后缺乏稳定的任务进展。

### 5. 已尝试三个事件控制的新候选方向

为了避免行人永久阻塞或机械循环，我们增加了“接近后触发、持续一段时间、
随后释放”的事件控制能力，并尝试了三个候选方向：

| 候选方向 | 当前结果 |
|---|---|
| 领行人突然停车后释放 | 已实跑；Base 碰撞，但包含静态几何干扰，PGRR 规划失败 |
| 双行人收口后释放 | 已实跑；Base 和 PGRR 都在终点附近超时 |
| 接近目标后一次性侧向横穿 | 已完成事件契约，尚未生成并运行 Arena 场景 |

前两个负结果已经保存，没有通过换种子或调阈值来追求理想结果。

### 6. 已整理现有论文证据

在冻结的 120 个匹配条件中，共有 26 个条件出现“Base 未到达、PGRR 到达”，
分布在 5 个原有场景族。我们从中整理了 8 条代表性 episode 记录，用于说明
PGRR 如何在某些具体条件下完成而 Base 失败。

这里必须明确：这 8 条只是已有结果中的定性例子，不是教授要求的 8 个场景，
也不能用来代替场景级重复验证。正式统计结论仍来自完整的 120 条件实验。

### 7. 已推进作业二：把大节点逐步拆成可测试模块

#### 7.1 作业二要解决的问题

原来的 `RecoveryManagerNode` 同时负责接收 ROS 消息、整理模型观测、筛选动作、
调用策略、管理恢复状态和发布执行命令。结构审计显示该类约 1873 行、包含 52 个
方法，其中 `_select_decision` 和 `_decision_step` 都超过 200 行。

这种结构目前可以运行，但存在两个问题：一是修改任何一部分都可能影响整个运行链；
二是许多纯计算规则只能启动 ROS/Arena 后才能间接检查，难以单独写测试。因此作业二
的目标不是重写算法，而是先把边界清楚、风险较低的部分抽成纯 Python 模块，同时证明
抽取前后行为一致。

#### 7.2 已完成第一层制品与流程接口

按照老师建议，我们新增了 `ramp_core.pipeline` 最小接口层：

- `contracts.py`：定义场景、数据、checkpoint 和评测制品的请求/结果契约；
- `io.py`：统一处理仓库相对路径与 SHA-256 校验；
- `ports.py`：定义 CLI 与内部 service 之间的可替换接口。

随后选择只读 DAgger 分析脚本完成第一例适配：

```text
argparse -> request dataclass -> service -> 原格式输出
```

旧命令参数、输出文件名和终端提示保持不变。这说明接口层可以加入现有项目，而不要求
用户改变原来的使用方式。

#### 7.3 已完成观测构建器原型和离线等价验证

我们从大节点中选择风险较低的“观测整理”边界，新增纯 Python
`RecoveryObservationBuilder`。它负责把机器人状态、目标、路径、LiDAR 历史、速度
和基础规划器状态整理成模型需要的固定输入。

该接口具有三个重要边界：

- 不依赖 ROS，固定输入即可单独测试；
- 不接收行人真值等特权信息，避免测试时泄漏训练信息；
- 不改变目标、动作阈值、恢复状态机或神经网络。

我们使用固定种子生成 32 组边界输入，同时运行旧观测逻辑和新 Builder。测试覆盖
空/短/长路径、不同 LiDAR 历史长度和不同进展历史长度。七个数组字段均达到：

- 32/32 输入输出元数据一致；
- 32/32 精确等价；
- 最大绝对误差为 0；
- mismatch 为 0。

这证明新 Builder 在覆盖到的纯计算规则上精确复现旧逻辑。

#### 7.4 已完成默认关闭的运行时影子比较框架

为了进一步验证真实 ROS 数据，我们没有直接让新 Builder 接管控制，而是把它作为
默认关闭的 shadow 路径接入：

```text
真实控制：旧观测 -> PGRR
诊断支路：相同输入 -> 新 Builder -> 只比较、不控制机器人
```

当前已经完成：

- shadow 默认关闭，旧观测始终是权威控制输入；
- 开启后逐字段比较，不保存不断增长的逐样本大数组；
- 候选 Builder 即使异常，也只记录 mismatch，不会中断旧控制路径；
- 汇总器支持并发安全，8 线程共 1000 次混合更新的计数完全正确；
- 节点结束时可以输出一次机器可读的等价性汇总；
- 启动前门禁会拒绝冻结测试路径、test split 和重复 episode ID；
- 五个运行相关源码已经通过 SHA-256 核对并安全同步到 WSL。

相关 Builder、shadow、ROS 参数、异常隔离和验证器测试均已通过。这里的关键原则是：
诊断代码不能反过来改变机器人行为。

#### 7.5 已完成动作掩码和恢复进展的可解释接口

除了观测构建，我们还增加了默认关闭的 mask trace，用来回答“21 个临时子目标分别
在哪一层被删除”。目前可以区分地图、LiDAR 安全扫描、路径走廊和方向让行等过滤层，
并记录每层前后还剩多少动作。

同时建立了纯 Python 的恢复进展接口，把一个恢复循环的开始距离、结束距离、恢复状态
和终止原因整理成可测试证据。这些接口帮助我们定位出新场景中方向候选不足的问题，
也为以后拆分策略协调器提供了测试基础。

#### 7.6 作业二目前的完成边界

已经完成的是：接口层、结构基线、观测构建器、离线精确等价探针、默认关闭的 ROS
shadow 框架、异常隔离、并发安全汇总、源码哈希门禁，以及 mask/progress 诊断接口。

尚未完成的是：

1. 真实 Arena episode 中的 observation-shadow 等价验收；
2. 让新 Builder 正式替换旧观测路径；
3. 将动作选择和恢复状态协调器从大节点中继续拆出；
4. 完成替换后的 ROS 时序、发布消息和最终回归验证。

因此目前可以说“第一阶段接口和安全迁移基础已经完成”，但不能说整个模块化重构已经
完成，也不能把 32/32 离线等价解释成真实 ROS callback 时序已经等价。

## 二、目前遇到的问题和障碍

### 1. 八个场景的任务还没有完成

教授要求的是八个可独立定义、可重复验证，并能体现 PGRR 相对 Base 优势的
场景，而不是八次单独成功。当前新开发场景中，还没有一个同时满足：

1. Base 明确失败；
2. PGRR 成功到达；
3. 差异来自目标动态交互，而不是静态墙体或启动故障；
4. 在多个预先固定的种子或重复中表现稳定。

所以目前严格意义上的合格进度是 0/8。已有工作仍然有价值，但不能误报为
八个场景已经完成。

### 2. 新场景越困难，PGRR 越容易变得过于保守

目前的新场景能够让 Base 碰撞，但也会使 PGRR 长时间等待、反复后退或规划
失败。这说明单纯增加行人、缩小通道或提高冲突强度，不一定能产生有价值的
比较，反而可能让所有方法都失败。

### 3. 恢复候选动作不足

动作掩码、安全距离和方向约束叠加后，方向性临时子目标经常全部被删除。
PGRR 虽然避免了危险动作，却没有足够的可行方向完成绕行和重新接入原路径。
这是当前最明确的算法泛化障碍。

### 4. 继续修改场景存在“按结果调场景”的风险

如果看到一次结果不好就改变位置、时间或随机种子，直到出现 Base 失败、PGRR
成功，那么最终场景可能只是人为筛选出来的偶然结果。后续必须先固定场景级
晋级标准和重复方式，再运行实验。

### 5. 是否允许修改算法或重新训练尚未确定

如果只改变场景而不改变 PGRR，可能继续出现“无碰撞但无法完成”。如果调整
候选生成、方向约束、动作掩码或重新训练 DAgger，就已经进入新的算法研究，
需要重新划分 train/validation，并在模型确定后建立新的 held-out test。

### 6. 部分正式实验原始轨迹没有保留在当前工作副本

正式统计表和 episode 信息仍然完整，一个代表性案例也有已经验证的轨迹图；
但另外一些 episode 缺少原始 JSONL 和 sidecar，因此不能重新绘制真实轨迹。
不能通过重跑冻结测试或人工补造数据来填补这一缺口。

### 7. 作业二还缺少真实运行时等价证据

新观测 Builder 已通过 32/32 离线精确等价，但真实 ROS 环境还包含消息回调时序、
缓存更新、目标切换和节点销毁顺序。当前尚未产生一份通过严格验证器的 Arena shadow
运行证据。因此旧观测仍然必须保持权威，暂时不能删除或替换。

## 三、后续实验需要确定的事情

### 1. 八个场景之间需要有多大差异

需要向教授确认：

- 是否必须是八种完全不同的交互机制；
- 还是允许在同一大类下，使用明显不同的几何、行人数、遮挡方式或运动时序，
  形成独立场景。

我们建议不能仅靠更换随机种子把同一场景算成多个场景。

### 2. 一个场景达到什么标准才算合格

建议在继续筛选前预先确定：

- Base 需要出现哪种失败：碰撞、超时或规划失败是否都算；
- PGRR 是否必须成功到达，而不能只做到“没有碰撞”；
- 每个场景使用多少个固定种子或重复；
- 至少多少次重复必须出现 Base 失败、PGRR 成功；
- 是否还需要与 Standard、Heuristic 和 Uniform BC 比较；
- 是否同时设置碰撞率、成功率、时间、路径长度和恢复次数等指标。

建议把“PGRR 成功到达”作为必要条件，并使用多个预先固定的重复，避免把偶然
成功当成场景级结论。

### 3. 下一阶段是否允许修改恢复机制

需要教授确定下一阶段属于哪一种：

**方案 A：保持算法不变，只继续寻找适合展示现有 PGRR 优势的场景。**  
优点是保持现有论文边界；缺点是可能很难补足八个稳定场景。

**方案 B：允许在独立 train/validation 上改进恢复候选和方向约束。**  
优点是能直接解决已发现的恢复瓶颈；缺点是需要重新验证，可能还要重新训练
DAgger，并建立新的 held-out test。

我们不能在当前冻结测试上边看结果边改算法。

### 4. 后续优先做场景筛选还是算法改进

如果教授希望先完成八个场景，应先固定晋级协议，然后批量测试若干不同机制
的候选。如果教授认为现有 PGRR 在新场景中的完成性不足更值得研究，则应先
处理“方向候选被清空”和“恢复后没有进展”的问题，再重新进行场景筛选。

### 5. 八个场景在论文中承担什么作用

需要确认八个场景是：

- 仅作为直观案例和可视化展示；
- 还是需要形成新的定量实验表；
- 是否要替代或补充现有 120 条件正式实验；
- 每个场景是否都需要轨迹图、恢复时间线或视频。

我们的建议是：保留现有 120 条件结果作为总体统计主证据，八个新场景作为
场景级扩展实验。二者分开报告，不能混为同一组统计。

### 6. 是否可以取得缺失的原始实验归档

如果教授或实验服务器仍保存正式运行的 JSONL、metadata 和 outcome sidecar，
可以恢复更多真实轨迹图；如果无法取得，则论文应只使用当前已有的一个验证
轨迹图和完整结果表，不能补画不存在的数据。

### 7. 作业二第一阶段以什么作为验收终点

需要教授确认作业二近期交付到哪一层：

- 以“接口层 + 离线等价测试 + 默认关闭 shadow”作为第一阶段完成；
- 还是必须再完成一次非冻结 Arena shadow，并证明真实消息下零 mismatch；
- 是否在 shadow 通过后立即让新 Builder 接管观测路径；
- 或者继续保持双路结构，先开始拆分动作选择/决策协调器。

我们的建议是先完成一次非冻结 train-only Arena shadow 验收。只有比较次数大于零、
全部字段等价、mismatch 为零、诊断异常为零，并确认旧路径始终控制机器人，才考虑正式
切换 Builder。切换后再运行回归测试，不应同时拆分决策协调器，以免问题难以定位。

## 四、建议与教授交流时重点确认的五个问题

1. 八个场景是否必须对应八种完全不同的交互机制？
2. 每个场景需要多少次固定重复，以及怎样才算 PGRR 稳定优于 Base？
3. 后续是否只筛选场景，还是允许修改恢复候选、方向约束并重新训练？
4. 八个场景在论文中是定性展示，还是需要作为一组新的定量实验？
5. 作业二第一阶段是否以 Arena shadow 等价通过为验收点，之后才正式切换 Builder？

## 五、当前阶段的一句话总结

> 我们已经完成环境、正式评测、八类扩展原型、恢复失败诊断、事件控制候选、
> 论文证据整理，以及作业二的接口层、观测构建器和安全 shadow 框架；当前主要
> 障碍是 PGRR 在困难新场景中能够避免碰撞，却经常不能恢复到目标，同时作业二
> 还缺真实 Arena shadow 等价证据。教授要求的八个场景尚未完成，下一步应明确
> 场景差异、晋级标准、重复次数、是否允许修改算法及作业二验收边界。
