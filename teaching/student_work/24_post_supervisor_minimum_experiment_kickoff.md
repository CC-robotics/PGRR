# 教授确认后：独立扩展实验的最小启动清单

日期：2026-08-28  
状态：执行前检查表；现在不创建实际场景、不运行训练或正式评测。

## 0. 先记录教授确认的四项输入

在开始任何新的配置或代码前，先把以下内容写入新的实验设计记录：

```text
研究问题：________________________________________
优先场景族：______________________________________
新场景用途：仅测试扩展 / 重新训练覆盖 / 两者严格分开
主要统计终点：____________________________________
```

若这四项没有答案，最多只能继续做图、模板和只读分析，不应擅自启动训练或大规模运行。

## 1. 第一个可执行的小里程碑：单条件基础设施 smoke

目标不是获得算法结果，而是确认一个新场景在既有环境中可以稳定运行并产生预期交互。

完成条件：

- 新场景采用独立、教授确认的 `benchmark_id` 与输出目录；
- 有一个明确的 `scenario_id`、地图 ID、机器人起终点、静态障碍和行人路线；
- 指定显式 seed；同一 seed 再运行时场景 JSON/manifest 哈希一致；
- Gazebo/ROS 有 clock、tf、LiDAR、odom、导航 action；
- 原始日志含有 `condition_key` 和全部终止类别字段；
- 只跑少量基础设施条件，不计算论文显著性，也不调阈值。

## 2. 第二个里程碑：场景校准，而不是“挑最好看的结果”

仅在教授确认的一个场景族内，做低/中/高难度的小样本校准。要回答：

| 要检查的问题 | 合格表现 |
|---|---|
| 交互真的发生了吗？ | 行人与机器人在预期时空位置接近，非“行人提前离开”。 |
| 场景可通行吗？ | 至少存在合理的等待、后退、横向或重规划恢复可能。 |
| 日志完整吗？ | 能收集终止、距离、路径、触发、恢复动作、尝试溯源。 |
| 基线难度合理吗？ | 不是全部轻易成功，也不是因几何无解而全部失败。 |
| 方法公平吗？ | 所有方法可使用同一组 `condition_key`。 |

校准记录必须保存在独立目录，并写明其仅用于设计确认；不能混进正式 held-out test 统计。

## 3. 第三个里程碑：冻结独立实验计划

在正式训练/测试前，锁定以下版本：

- 场景 YAML/JSON、地图、行人参数、seed 范围和重复次数；
- train / validation / held-out test 的 `scenario_id + seed` 列表；
- 使用哪些 runner（Base、Standard、Heuristic、Uniform BC、PGRR）；
- 若训练，专家标签版本、训练配置、checkpoint 选择规则；
- 主统计终点与校正方案；
- 输出目录、并发、重试定义与 manifest 哈希。

冻结后，**validation 不再用于调场景，held-out test 不再用于选模型或阈值**。

## 4. 若教授优先要求作业二的代码重构

采用最小、可回滚顺序：

1. 只新增纯 Python 的观测构建器接口与合成等价测试；
2. 复跑既有 action mask、state machine、recovery options、ML 输入测试；
3. 再把决策规则协调器提炼为纯函数/显式 memory；
4. 仍由 ROS 节点保留订阅、参数、执行、发布和原始目标恢复；
5. 每一步只改变一个模块，记录测试结果，再进入下一步。

对应设计材料：`15_observation_builder_extraction_boundary.md`、
`16_decision_coordinator_extraction_boundary.md`、
`17_refactor_synthetic_fixture_plan.md`。

## 5. 启动后每周可向教授汇报的最小格式

```text
本周完成：一个具体可验证项目
证据：配置/manifest/测试输出/图的路径
未完成原因：若有，说明环境、数据或设计依赖
下一步：一个不超过一周的可验证目标
需要教授确认：仅列影响研究方向或实验公平性的决定
```

这样可以保持节奏，也不会把“环境进度”误报为“算法效果”。
